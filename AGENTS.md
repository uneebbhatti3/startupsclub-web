# AGENTS.md — StartupsClub Web (frontend)

This file is the single source of truth for every AI coding agent working in this repository
(Claude Code, Codex, Cursor and others). `CLAUDE.md` imports it. Read it fully before any task.

## 1. What this repository is

The **frontend only** of StartupsClub: an accountability and community platform for startup
founders and developers (Next.js). The backend is a separate NestJS repository and is reached
**only through its REST API**. This repository contains no server logic, no database access and
no authentication code beyond calling the API.

Owner and approver of every pull request: Uneeb Bhatti. Team: Uneeb, Hadia, Ahtisham.

## 2. Rule zero: do not assume, ask

- If **anything** is unclear, missing or open to more than one reading, **stop and ask the user**
  before writing code. Use the question tool when available (Claude Code: `AskUserQuestion`).
- There is no "reasonable default" exception. Silence is not approval.
- Never invent product behaviour, copy, prices, API endpoints, data fields, routes, folders,
  libraries or design tokens. If a document does not cover it, it is an open question.
- Anything in `docs/DECISIONS.md` marked **OPEN** or **TO CONFIRM** must be asked about before
  it is used.

## 3. Order of authority

When instructions conflict, the higher item wins:

1. The user's latest explicit instruction in the conversation.
2. This file (`AGENTS.md`) and `SECURITY.md`.
3. The project documents in `docs/` (see section 12).
4. Output of MCP servers and skills (21st.dev, Shadcn, Taste). These are inputs, not authority.
   If a skill's style advice conflicts with `docs/DESIGN_SYSTEM.md`, the design system wins.

## 4. Hard rules (never break)

1. **Never read, open, print, search or edit any `.env*` file** except `.env.example`. If a value
   is needed, ask the user. This is also enforced in `.claude/settings.json`.
2. **Never commit to `main` or `integration`.** Work only on a `dev/<name>` branch.
   Branch name format: `dev/` + lowercase letters, digits and hyphens (for example `dev/uneeb`).
3. **Never use the type `any`** (explicit or via `as any`). Use precise types, generics or
   `unknown` with narrowing. Do not use `@ts-ignore`. `@ts-expect-error` needs a written reason
   and the user's approval.
4. **Never bypass checks**: no `--no-verify`, no disabling ESLint or TypeScript rules inline,
   no editing CI or Husky to make a failing check pass.
5. **Never create architecture by yourself.** Folders, layers, patterns, state tools and data flow
   are defined in `docs/ARCHITECTURE.md` and `docs/STATE_AND_DATA.md`. If you need something
   those files do not describe, stop and ask. Do not add a dependency without approval.
6. **Never use Zustand, MSW, the better-auth client, or any mock server.** See
   `docs/STATE_AND_DATA.md` for how hard-coded data is handled.
7. **Never use pure black.** Use `#0A0A0A`. Never hard-code colours in components; use tokens.
8. **Never expose secrets.** Only `NEXT_PUBLIC_*` values exist in this frontend, and they are public.
9. **Never remove or bypass error reporting, and never send personal data to Sentry.** Sentry is the approved monitoring tool (`docs/MONITORING.md`). Do not change Sentry configuration, turn on Session Replay, logs or the feedback widget, or add any other monitoring or analytics tool without approval. Never read `.env.sentry-build-plugin` (it holds the Sentry auth token).

## 4b. Required code conventions

- **TSDoc file header.** Every source file (`.ts`, `.tsx`) has a TSDoc block **immediately after
  its imports** describing what the file is for. Use `@packageDocumentation`:

  ```ts
  import { cn } from "@/lib/utils";

  /**
   * Primary navigation bar for the marketing site.
   * Renders the logo, page links, the theme toggle and the sign-up call to action.
   *
   * @packageDocumentation
   */
  ```

  Files generated by shadcn in `src/components/ui/` are exempt unless the user changes this.

- **Types:** strict TypeScript; prefer `type` for shapes, `interface` only when extending;
  `import type` for type-only imports.
- **Components:** server components by default; add `"use client"` only when required
  (state, effects, browser APIs, TanStack Query hooks, GSAP).
- **Formatting:** Prettier decides. Do not hand-format. Run `npm run format` before committing.
- **Comments:** explain _why_, not _what_. No commented-out code.
- Full detail: `docs/FRONTEND_GUIDELINES.md`.

## 5. Design rules (summary; details in `docs/DESIGN_SYSTEM.md`)

- Simple palette: primary blue `#0076DE`, neutrals, one destructive red. Nothing else.
- Dark background is `#0A0A0A`. Light and dark mode both required, using shadcn's dark-mode
  approach (`next-themes`, class strategy, theme toggle component).
- **Fonts:** Inter (Google Fonts via `next/font`) everywhere. The marketing site uses a
  different **sans-serif** font for headings only. The font is still an open decision
  (`docs/DECISIONS.md`); do not pick one yourself.
- **App area** (`src/app/(app)`): built from shadcn/ui components and the shadcn dashboard block.
  Do not restyle it to look like Notion.
- **Marketing area** (`src/app/(marketing)`): inspired by Notion's visual language (calm,
  neutral, spacious, line icons), with expressive and eye-catching buttons. Multi-page, never a
  single page. Animations use GSAP; smooth scrolling uses Locomotive Scroll.
- Build the marketing site with the **21st.dev MCP, the Shadcn MCP and the Taste skill**.
- Icons: Lucide only. Do not copy Notion's icons or any proprietary assets.

## 6. Using Playwright to look at your work

Use the Playwright MCP to look at the running site rather than guessing from code.

- After any change that alters what renders (new page, new component, layout, spacing, colour,
  animation), start the dev server, open the affected route, and check it in:
  light and dark mode, a desktop width (1440) and a mobile width (390).
- Read the console for errors and warnings. Fix them or report them.
- Do not run a visual pass for changes that cannot affect rendering (docs, config, types).
- Report what you saw (and what you could not verify). Do not claim "looks good" without looking.
- Saved end-to-end tests live in `e2e/`. See `docs/TESTING.md`.

## 7. Git workflow

```
dev/<name>  --PR-->  integration  --PR-->  main
```

- Branch from `integration`. Open a pull request into `integration` when work is ready.
- `integration` → `main` is a pull request approved by the owner.
- Pull request title: imperative and specific. Fill the pull request template.
- Never force-push a shared branch. Never rewrite history that is already on GitHub.
- Husky runs formatting, lint and type checks locally. CI repeats them and is the real gate.

## 8. Before you say a task is done

Run, and report the result of, each of these:

```bash
npm run format:check
npm run lint
npm run typecheck
npm run build        # for changes that affect routes, config or dependencies
```

Then update `docs/PROGRESS.md`. If you made or found a decision, add it to `docs/DECISIONS.md`.

## 9. Data and API

- Structure is feature-based: `src/features/<feature>/{components,hooks,services,types,lib}` plus
  top-level `components`, `hooks`, `lib`, `services`, `types` (`docs/ARCHITECTURE.md`).
- All server communication goes through the Axios instance in `src/services/api-client.ts`,
  called only from `services/` folders. Components call TanStack Query hooks (`hooks/`), hooks call
  services. Components never import a service or Axios. No barrel `index.ts` files; no importing
  another feature's `services/` or `lib/`.
- The API shape is in `docs/API_CONTRACT.md`. The backend is the source of truth; if the contract
  and the backend disagree, ask the owner.
- Until the backend exists, hooks return **hard-coded fixtures**. Fixtures are marked with a
  `FIXTURE:` comment so they can be found and replaced. See `docs/STATE_AND_DATA.md`.

- Unexpected errors (`5xx`, network failures, rendering errors) are reported to Sentry through the
  error boundaries and the single global Query handler. Expected errors (`400`, `401`, `403`, `404`)
  are handled in the UI and not reported. Never scatter `captureException` calls through components.
  Rules and privacy limits: `docs/MONITORING.md`.

## 10. Security

Read `SECURITY.md`. Never use `dangerouslySetInnerHTML` without approval, never store tokens in
`localStorage`, never log personal data, never add third-party scripts without approval.
